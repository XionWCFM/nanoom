설정 파일은 저장소 루트의 `nanoom.config.json`입니다. 에디터 자동완성을 위한 JSON 스키마 생성:

```bash
nanoom schema --output nanoom.schema.json
```

설정에 추가:

```jsonc
{
  "$schema": "./nanoom.schema.json"
}
```

알 수 없는 필드는 명확한 에러 메시지와 함께 거부됩니다.

## 최상위 필드

| 필드 | 타입 | 기본값 | 필수 | 설명 |
| --- | --- | --- | --- | --- |
| `$schema` | string | — | 아니오 | JSON 스키마 경로 또는 URL |
| `group` | object | — | **예** | 하나 이상의 명명된 작업 그룹 |
| `globalDependencies` | string[] | `[]` | 아니오 | 바뀌면 모든 프로젝트에 영향 주는 글로브 |
| `workspace` | object | — | 아니오 | 자동 워크스페이스 발견 오버라이드 |

## 그룹

`group` 아래 각 키는 그룹 이름입니다 (예: `ci`, `e2e`, `release`). 그룹은 독립적 — 한 프로젝트가 여러 그룹에 다른 규칙으로 들어갈 수 있습니다.

```jsonc
{
  "group": {
    "ci": {
      "tasks": ["lint", "test", "build"],
      "concurrency": 6,
      "rules": [{ "name": "@app/web", "isolate": ["test"] }]
    }
  }
}
```

### 그룹 필드

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `tasks` | string[] | **예** | 이 그룹이 실행할 package.json 스크립트 이름들 |
| `concurrency` | integer (>0) | **예** | 그룹당 최대 매트릭스 항목 수. 초과분은 공유 잡에 배칭 |
| `rules` | Rule[] | 아니오 | 프로젝트별 오버라이드 (아래 참고) |

## 규칙

규칙은 프로젝트 이름으로 대상을 지정하고 그룹 내 동작을 바꿉니다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `name` | string | **필수**. 이 규칙을 적용할 프로젝트 이름 |
| `ignore` | boolean | 이 프로젝트를 그룹에서 완전히 제외 |
| `isolate` | string[] | 이 프로젝트의 나열된 작업을 전용 매트릭스 항목으로 만듦 (배칭 안 함) |
| `shard` | ShardRule[] | 이 프로젝트의 작업을 N개 샤드로 분할 |

### ShardRule

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `task` | string | 샤딩할 작업 이름 (그룹의 `tasks`에 있어야 함) |
| `shard` | integer (≥2) | 샤드 개수 |

예시:

```jsonc
{
  "name": "@slow/e2e",
  "ignore": false,
  "isolate": ["test:e2e"],
  "shard": [{ "task": "test:e2e", "shard": 4 }]
}
```

샤딩은 `"shard": 1..N`을 가진 매트릭스 항목들을 냅니다. 잡 안에서 `nanoom run`이 `NANOOM_SHARD_INDEX`와 `NANOOM_SHARD_TOTAL`을 내보내니, 러너에 넘기세요 (Jest `--shard=$INDEX/$TOTAL`, Playwright `--shard=x/y` 등).

## 워크스페이스 발견

기본적으로 nanoom은 이 순서로 워크스페이스 설정을 찾습니다:

1. `pnpm-workspace.yaml`
2. `turbo.json`
3. `nx.json`
4. 루트 `package.json` → `workspaces` 필드 (배열 또는 `{ packages: [] }`)

후보 디렉터리마다 `package.json`이 있어야 하며, 그 `name`이 프로젝트 이름이 됩니다 (없으면 디렉터리 이름).

### 글로브로 오버라이드

```jsonc
{
  "workspace": {
    "include": ["packages/*", "apps/*", "services/**"],
    "exclude": ["**/deprecated/**"]
  }
}
```

| 필드 | 타입 | 기본값 | 설명 |
| --- | --- | --- | --- |
| `include` | glob[] | `["packages/*", "apps/*"]` | 후보 디렉터리들 |
| `exclude` | glob[] | `[]` | 제외할 디렉터리들 |

글로브는 저장소 루트 기준 상대 경로에 매치. 문법: `*`, `**`, `?`, `[abc]`, `{a,b}`.

## 의존성 그래프

프로젝트 간 에지는 네 가지 의존성 종류 전부(`dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`)에서 pnpm 스타일 해석으로 도출:

| 지정자 | 내부 에지? | 조건 |
| --- | --- | --- |
| `workspace:*`, `workspace:^x.y.z`, `workspace:~x.y.z` | ✅ 항상 | 워크스페이스 프로토콜 |
| `link:…`, `file:…` | ✅ 항상 | 로컬 링크/파일 |
| 일반 세므버 (`^1.0.0`, `~2.1.0`, `>=1 <3`, `1.0.0`, `||` 합집합) | ✅ 로컬 버전이 범위 만족 시 | 로컬 패키지로 해석 |
| 해석 불가 / 레지스트리 범위 | ❌ 아니오 | npm 레지스트리 가리킴 |

영향 확장은 **역방향 에지**를 따라 전이적으로 갑니다: 리프 라이브러리 하나 바꾸면 직·간접 피의존 전부가 포함.

## 에러 처리

검증 에러는 실행 가능한 메시지를 포함합니다:

- 알 수 없는 최상위 필드 → `"알 수 없는 필드 'typo', 'group'을 의도하셨나요?"`
- 0 또는 없는 `concurrency` → `"concurrency는 양의 정수여야 합니다"`
- 빈 `tasks` 배열 → `"그룹 'ci'는 최소 한 개 작업이 필요합니다"`
- `name` 없는 규칙 → `"규칙에 'name' 필드가 필요합니다"`
- 알 수 없는 프로젝트 → `"규칙이 알 수 없는 프로젝트 'x'를 참조합니다"`

모든 에러에 JSON 경로 포함 (예: `group.ci.rules[0].name`).

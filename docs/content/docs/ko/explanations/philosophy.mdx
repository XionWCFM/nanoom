## 한 가지 질문에 정확히 답하기

nanoom은 딱 하나만 합니다: 변경이 어떤 프로젝트에 영향을 주는지 판단하고, 그 답을 CI 기본 요소로 바꿉니다. 그 외는 설계상 범위 밖입니다.

## 지루한 기술 쓰기

- **Git이 데이터베이스.** 바뀐 파일은 실제 병합 베이스 기준 `git diff`에서 나옵니다. 상태 파일 없음, 무효화할 캐시 없음, 데몬 없음.
- **단일 정적 바이너리.** Rust로 작성; Actions가 이미 제공하는 것 외에 러너에 설치할 런타임 없음.
- **공개 스키마 있는 JSON 설정.** 자동완성과 검증이 공짜; 배울 YAML 앵커나 DSL 없음.

## 영리한 캐싱보다 올바른 전파

의존성 그래프는 pnpm과 같은 해석 규칙을 씁니다:

- 워크스페이스 프로토콜 링크 (`workspace:*`, `link:`, `file:`) — 항상 내부 에지.
- 일반 세므버 범위 — 로컬 버전이 범위를 만족할 때만 내부 에지.
- 영향 확장은 역방향 에지를 따라 전이적으로 갑니다.

약간 더 돌리는 거짓 양성(불필요하게 실행)은 괜찮지만, 조용히 빼먹는 거짓 음성(깨진 걸 건너뜀)은 피합니다. 결정적 출력 순서로 매트릭스가 매 실행마다 재현 가능합니다.

## GitHub Actions 네이티브

출력이 Actions 방언입니다: `{ "include": [...] }` 매트릭스, `$GITHUB_OUTPUT` 결과 줄, Actions가 정확히 세팅하는 이벤트 환경 변수. nanoom은 플랫폼을 대체하지 않고 조합합니다.

## 우아한 저하

- 얕은 클론? 자동으로 깊게 팜 (`--depth 128`, 실패 시 두 배).
- 포크 PR? 헤드 저장소 기준으로 풂.
- 공통 조상 없음? 스택 트레이스 대신 명확한 에러로 리베이스하라고 알려줌.

## nanoom을 쓰지 말아야 할 때

원격 빌드 캐싱, 감시 모드 개발 서버, 코드 생성 파이프라인, 500+ 패키지에 무거운 빌드 그래프가 필요하면 Turborepo나 Nx를 쓰세요. 그 도구들은 다른 문제를 위해 만들어진 훌륭한 도구들입니다.

nanoom은 그 아래에 있는 빠르고 의존성 없는 층입니다: **감지 → 매트릭스 → 구성 → 집계**.

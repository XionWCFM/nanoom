nanoom은 모노레포 CI에서 **"이 변경이 어떤 프로젝트에 영향을 주는가?"**라는 한 가지 질문에 정확히 답합니다. 그 답을 GitHub Actions 기본 요소(잡 매트릭스, 프로젝트별 작업 실행, 최종 상태 게이트)로 바꿔서, 변경과 무관한 패키지 테스트를 멈추게 합니다.

## 문제 상황

모노레포에서는 모든 푸시가 CI를 트리거합니다. 일반적인 방식은 **모든 패키지의 모든 작업**을 매번 실행합니다:

- 패키지 30개 × 작업 3개 = **90개 잡** — README만 고쳐도 똑같이 돔니다.
- 피드백 루프가 몇 분에서 한 시간으로 늘어납니다.
- 불안정하고 비싼 러너가 헛되이 돈을 씁니다.

기존 도구들은 데몬, 원격 캐시, 록파일, 코드 생성 플러그인 같은 무거운 기계로 이 문제를 풉니다. 대규모에선 훌륭하지만, 도입하고 운영할 게 너무 많습니다.

## nanoom이 작동하는 방식

```
감지 → 매트릭스 → 구성 → 집계
```

1. **감지** — `git diff`로 바뀐 파일을 워크스페이스 프로젝트에 매핑한 뒤, 의존성 그래프를 따라 역방향으로 확장합니다. `lib`이 바뀌면 `lib`을 링크하는 모든 프로젝트가 영향받습니다.
2. **매트릭스** — `{ "include": [...] }` JSON을 내보내 `strategy.matrix`가 바로 소비하게 합니다.
3. **구성** — 매트릭스 잡 하나가 `(프로젝트, 작업)` 쌍 하나를 `nanoom run`으로 실행합니다.
4. **집계** — 마지막 `status` Action이 실패하거나 일관되지 않은 매트릭스 결과를 거부합니다.

## 빠르게 맛보기

```bash
nanoom affected --base main --head HEAD

Has changes: true

Group: ci (2 entries)
  - @app/web      → test
  - @lib/ui       → test

Group: e2e (0 entries)
```

README만 고친 커밋은 **테스트 잡 0개**를 만듭니다. 리프 라이브러리를 고치면 그 라이브러리와 링크된 앱만 테스트합니다.

## nanoom이 의도적으로 하지 않는 것

- 데몬, 백그라운드 프로세스, CI용 감시 모드 없음
- 비용 내고 호스팅할 원격 캐시 서비스 없음
- 자체 록파일 포맷 없음 — 여러분의 git 히스토리가 곧 상태입니다.

500개 이상 패키지에서 분산 캐싱이 필요하면 Turborepo나 Nx로 졸업하세요. 그전까지는 nanoom이 단일 정적 바이너리와 JSON 설정 파일만으로 대부분의 이득을 줍니다.

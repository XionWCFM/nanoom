nanoom answers one question for your monorepo CI: **which projects does this change affect?** It turns the answer into GitHub Actions primitives — a job matrix, per-project task runs, and a final status gate — so you stop testing packages your change never touched.

## The problem

In a monorepo, every push triggers CI. The naive approach runs **every task in every package** on every push:

- 30 packages × 3 tasks = **90 jobs** — even when you changed a README.
- Feedback loops stretch from minutes to an hour.
- Flaky, expensive runners burn money for nothing.

Existing tools solve this with heavy machinery: daemons, remote caches, lockfiles, codegen plugins. Great at scale, but a lot to adopt and operate.

## How nanoom works

```
detect → matrix → compose → aggregate
```

1. **Detect** — map changed files (from `git diff`) onto workspace projects, then expand through the dependency graph: change `lib`, and every project that links `lib` is affected too.
2. **Matrix** — emit `{ "include": [...] }` JSON that `strategy.matrix` consumes directly.
3. **Compose** — each matrix job runs one `(project, task)` pair via `nanoom run`.
4. **Aggregate** — a final `nanoom status` step fails the workflow if anything failed.

## Quick taste

```bash
$ PULL_REQUEST_BASE_REF=main nanoom affected

Has changes: true

Group: ci (2 entries)
  - @app/web      → test
  - @lib/ui       → test

Group: e2e (0 entries)
```

A README-only change produces **zero test jobs**. A change in a leaf library tests that library and everything that links it — nothing else.

## What nanoom deliberately does not do

- No daemon, no background process, no watch mode in CI.
- No remote cache service to pay for or host.
- No lockfile format of its own — your git history *is* the state.

If you need distributed caching at 500+ packages, graduate to Turborepo or Nx. Until then, nanoom gets you most of the win with a single static binary and a JSON config file.

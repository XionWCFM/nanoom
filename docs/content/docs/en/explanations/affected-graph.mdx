---
title: How the affected graph works
description: From explicit revisions to workspace task matrices
---

The calculation is deterministic for a repository state, config, base, and head:

1. Compare the explicit revisions with Git and list changed paths.
2. Discover workspaces from configured include/exclude globs and supported workspace metadata.
3. Build local dependency edges from all package dependency kinds. Registry ranges create an edge only when the local version satisfies npm semver.
4. If a global-dependency glob matches, select every workspace. Otherwise select workspaces containing changed paths.
5. Walk reverse edges transitively so dependents of a changed package are also affected.
6. For every group task, apply ignore rules and emit standard, isolated, or sharded matrix entries.

The CLI requires `--base` and defaults `--head` to `HEAD`. The GitHub Action resolves event context at its boundary and passes both revisions explicitly. This separation keeps the graph reusable outside GitHub.

An isolate rule produces one entry marked `isolate: true`. A shard count `N` produces `N` entries with one-based `shard` and `totalShards: N`. The same task cannot be both isolated and sharded.

No matrix-size setting silently drops work. Every selected `(workspace, task)` produces the required entry or shard entries. Consumers should assert the expected entry names and shard count, then execute all generated jobs.
